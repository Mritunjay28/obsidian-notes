### **Exceptions vs. Errors**

In Java, every problem condition is represented as an **object** rather than just a conceptual state.

| Dimension              | **Exceptions**                                                                                                          | **Errors**                                                                                                                  |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| **Definition**         | An abnormal, unexpected condition occurring during execution that is **recoverable and handleable** by application code | A **severe system failure** indicating conditions that application code and business logic are not designed to recover from |
| **Recovery**           | Developers can catch the issue, retry, take corrective action, or continue normal program flow                          | Cannot be recovered from within application code; execution terminates                                                      |
| **Typical Examples**   | `ArithmeticException` (e.g., dividing by zero), `FileNotFoundException` (missing external file)                         | `OutOfMemoryError` (Heap memory exhausted), `StackOverflowError` (Stack memory exhausted via infinite recursion)            |
| **Internal Mechanism** | JVM creates and throws an Exception object containing diagnostic details                                                | JVM creates and throws an Error object representing underlying environment exhaustion                                       |
|                        |                                                                                                                         |                                                                                                                             |

### **Why Exception Handling is Critical**
- **Default Behavior (No Handling)**:
    - When an unhandled exception occurs, the JVM terminates the program immediately, abruptly breaking the normal flow of control
    - Any lines of code situated after the failure point are **never executed
- **Benefits of Explicit Handling**:
    - **Maintains Control**: Prevents the JVM from forcefully crashing the application and keeps the execution flow within the developer's control
    - **Improves User Experience (UX)**: Instead of exposing raw system crashes or technical stack traces to end users (such as an SQL error when a database connection drops), the program can display informative fallback messages or default empty states
    - **Simplifies Debugging**: Provides predictable failure reporting and logging mechanisms.
## **Exception Lifecycle & The Call Stack**

#### **A. Internal JVM Throwing Mechanism**
When the JVM encounters an illegal operation (e.g., `5 / 0`):
1. It detects an illegal operation and interrupts normal execution
2. It instantiates an exception object with a descriptive message (e.g., `new ArithmeticException("divide by zero")`)
3. It throws this object and searches for an appropriate handling block

#### **B. Call Stack Unwinding & Default Exception Handling**
- Method invocations are pushed onto the **Stack memory**: `main()` pushes `methodA()`, which in turn pushes `methodB()
- If `methodB()` throws an exception:
    1. The JVM first checks whether `methodB()` contains a handler
    2. If unhandled, `methodB()` is **popped from the stack**, and the search unwinds to its caller, `methodA()`
    3. If unhandled by `methodA()`, it is popped, and the search moves to `main()
    4. If `main()` does not handle it, `main()` is popped, and the JVM activates **Default Exception Handling**: it terminates the program and prints the entire **stack trace** to the console.

#### **C. Anatomy of a Stack Trace**
A stack trace records the exact path of method calls leading to a failure:
- **Thread Context**: Indicates which thread failed (e.g., `Exception in thread "main"`)
- **Exception Class**: Fully qualified class name (e.g., `java.lang.ArithmeticException`, which resides in `java.lang` and requires no import)
- **Detail Message**: Explanation generated by the constructor (e.g., `/ by zero`)
- **Origin & Chain**: Follows the pattern `at ClassName.methodName(FileName.java:LineNumber)`, tracing backwards from the root failure point to the initial caller.

## **Handling Mechanisms: `try`, `catch`, and `finally`**
#### **A. The `try` Block**
- Contains **risky code** where exceptions may potentially be thrown at runtime.
- If no exception occurs, the block completes normally and skips attached `catch` blocks.
- If an exception occurs, execution inside the `try` block halts immediately at the failing line, jumping directly to a matching `catch` block.

#### **B. The `catch` Block**
- Acts like a parameterized handler taking an exception reference variable (e.g., `catch (ArithmeticException e)`).
- Defines the corrective logic to prevent program termination.
- **Available Methods on the Exception Object** **e**:
    - **e.getMessage()**: Retrieves the exception message string created by the JVM.
    - **e.printStackTrace()**: Prints the complete trace to the console or logs for diagnostic purposes without terminating the application.
- **Matching Rules & Multiple Catches**:
    - A `catch` block must match the exception type thrown; if an unmatching type is specified (e.g., catching `NullPointerException` when `ArithmeticException` is thrown), the exception remains uncaught and crashes the program.
    - Multiple consecutive `catch` blocks can be attached to a single `try` to handle different failure modes independently.

#### **C. `try-catch` vs. `if-else`**
- **if-else** **(Preventive)**: Avoids the problem altogether before it happens (e.g., checking `if (b != 0)` before dividing); no exception object is created.
- **try-catch** **(Reactive / "Try First")**: Attempts execution directly; if an abnormal condition occurs, the JVM instantiates and throws an exception object for structured recovery.

#### **D. The `finally` Block**
- **Execution Guarantee**: Always executes, whether an exception is thrown, caught, or completely absent.
- **Purpose (Clean-up Code)**: Used to close shared or external resources (e.g., file streams, database connections) to avoid resource locking and memory leaks, especially when code inside `try` exits prematurely due to an error.
- **try-finally** **Structure**: A `try` block can be combined directly with `finally` without an intermediate `catch` block; in this scenario, `finally` runs before the unhandled exception propagates out to the caller or JVM.
